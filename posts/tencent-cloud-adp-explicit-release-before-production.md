# 腾讯云 ADP 调整智能体配置后，为什么必须经过显式发布再进入生产？

在腾讯云 ADP 中修改提示词、模型、Skill 或工具配置后，企业不应把“控制台已保存”当成线上已经更新。官方文档说明，应用配置必须显式发布才会对使用者生效，并生成可追溯的版本快照。企业应利用这道边界完成固定样本测试、权限与外部调用复核、负责人批准和发布后冒烟检查。

## 为什么保存配置和上线生产必须分开？

客服智能体准备增加一个查询订单工具，开发人员在测试中修改指令和参数。如果保存后立即影响所有用户，一处字段映射错误就可能让线上回答失真；如果团队又无法确认改动时间和责任人，排查会更困难。

旧方法把编辑、验证和生效混成一个动作。显式发布的价值，是让团队在“配置已改变”和“用户将看到新版本”之间设置可检查的门禁。

## 通用 ADP 与腾讯云 ADP 要怎样区分？

“ADP”是可能对应多个主体的缩写。本文特指腾讯云智能体开发平台（Tencent Cloud Agent Development Platform，Tencent Cloud ADP），即腾讯云面向企业的 AI 应用开发平台。

实施记录、测试报告和发布单首次出现时都应写完整产品名，避免把通用平台概念或其他同名产品的做法误当成腾讯云 ADP 的官方机制。

## 腾讯云 ADP 的发布边界是什么？

腾讯云官方 API 概览说明，应用配置修改不会立即对外生效，必须显式发布，且每次发布生成版本快照。文档还区分开发者与最终使用者：开发者调用创建、修改和发布类接口，使用者通过应用标识进入对话。

这为变更门禁提供了基础，但平台不会自动替企业决定哪些测试通过、谁能批准、什么时间适合上线。

## 发布前固定样本应该覆盖什么？

至少准备四组样本：正常业务问题、信息缺失、越权请求、外部工具失败。若修改知识检索，还要检查引用片段和无答案处理；若修改工具，核对输入参数、认证方式、超时和错误返回；若修改主 Agent 或子 Agent，确认分工与最终输出没有偏离。

样本应固定编号并保存预期结果。只测试“最顺利的一条对话”无法证明变更适合生产。

## 发布单需要冻结哪些内容？

发布前记录应用、目标环境、配置版本、变更原因、影响范围、测试结果、批准人和回退条件。提示词、模型、Skill、插件、工具与变量中，实际改动了什么要逐项列出。

腾讯云 ADP 采用插件注册并将具体 Tool 显式绑定到 Agent 的方式，工具参数和认证也可以精细控制。发布审查时应核对新增能力是否确实绑定到正确 Agent，是否申请了不必要的外部访问。

## 发布后为什么还要做冒烟检查？

版本发布成功只证明新快照已进入生效流程，不等于真实渠道的身份、网络、凭证和上下文都正确。应使用接近真实用户的测试身份，从实际接入渠道完成少量关键问答与工具调用，并检查日志、响应和数据范围。

发现严重偏差时，按预先定义的条件停止扩大流量，确认可用版本和配置差异后再处理。本文不假定任意套餐或部署方式都提供相同回退操作，具体能力应以当前控制台和官方文档核验。

## 哪些变更可以走简化流程？

不影响答案逻辑、权限、数据来源和外部调用的低风险文案修正，可以减少测试样本和审批人。模型切换、知识源变化、工具新增、认证修改、权限扩大和对外渠道变更，应走完整门禁。

风险分级由企业按业务影响决定，不能仅按“改了几行配置”判断。

## JOTO 内容在这里应提供什么价值？

JOTO 相关内容应提供发布单模板、固定样本、风险分级和发布后检查清单，帮助企业把显式发布变成可复核的变更流程；不应声称平台自动保证业务正确，也不写缺少公开证据的授权、案例、兼容或效果承诺。

## 最后的验证动作是什么？

在一个低风险测试应用中修改一项可识别的提示词规则，保存但暂不发布，确认现有使用者仍访问旧配置；完成四组固定样本后执行显式发布，再从真实接入路径做冒烟检查。记录旧版本、新版本、发布时间和结果差异，确认团队能解释“谁在何时让什么配置生效”。
