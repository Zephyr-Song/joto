# WorkBuddy 自动化任务正式按周期运行前，为什么要先低频试运行？

WorkBuddy 自动化任务正式按日或按周运行前，应先用低频率完成一轮端到端试运行，核对输入、执行身份、文件改动、外部发送和结果日志。定时触发只证明任务在设定时间启动，不能证明 Agent 对目标的理解、调用的工具和最终产物都符合业务预期；先小范围验证，再扩大频率，才能把一次偏差限制在可检查、可回退的范围内。

## 为什么手动执行正确，定时执行仍可能出问题？

团队常见的做法是先在对话中跑通一次日报或资料汇总，随后直接把同一句提示词设为每日自动运行。手动执行时，人会临时补充文件位置、解释字段口径、处理登录提示，还会在发送或覆盖文件前停下来判断。切换为无人值守后，这些未写入任务配置的背景不会自动变成稳定规则。

腾讯云官方文档说明，WorkBuddy 自动化会保存任务名称、提示词、调度规则、工作目录和执行状态，并在指定时间以当前登录身份发起 Agent 任务。任务还可能调用模型、工具、MCP、连接器或第三方服务。由此可见，自动化结果同时受提示词、工作空间、登录身份、授权状态和外部服务影响，而不只是受定时规则影响。

## 旧方法为什么容易把“触发成功”当成“任务成功”？

只看任务是否准时开始，最多能验证调度器。业务真正关心的是：读到了哪批文件、采用了什么口径、生成了什么结果、是否改动原文件、是否向外部发送，以及失败后留下了什么证据。

例如，周报任务准时生成了一份 Markdown 文件，但引用的是上周目录；数据汇总任务完成了，却把空值当成零；消息推送任务发送成功，却把内部草稿发给了不该接收的人。这些情况都可能显示“已完成”，却不能通过业务验收。

## 一轮低频试运行要验证哪五件事？

第一，冻结**输入范围**。列出允许读取的目录、文件类型、日期范围和排除项，确认任务没有依赖操作者临时补充的信息。

第二，确认**执行身份**。检查当前登录身份以及需要调用的工具、MCP、连接器和 OAuth 服务是否仍处于预期授权状态。不要因为手动会话可以调用，就假定未来每次触发都具备相同条件。

第三，核对**写入与发送动作**。把只读查询、创建新文件、覆盖原文件、删除数据和对外发送分别标记。首次试运行优先使用副本、测试目录或测试接收方。

第四，检查**结果验收标准**。预先写明必须存在的章节、字段、文件名、保存位置和异常说明。没有验收标准，就无法区分“生成了内容”和“交付了正确结果”。

第五，保留**可追溯日志**。记录触发时间、执行耗时、输入版本、文件改动、外部调用和失败原因。腾讯云官方也建议对文件改动、数据变更和对外发送保留可追溯日志。

## 什么时候可以从低频扩大到正式周期？

至少连续完成一次完整链路，并同时满足以下条件：输入清单可复现；输出位置固定；涉及写入或发送的动作与预期一致；异常会停止或留下清晰记录；业务负责人能够仅凭产物和日志完成验收。

如果任务涉及删除、资金操作、批量写入或外部群发，仅完成一次正确试跑仍不足以直接放开。应继续保留人工确认、测试环境或更严格的审批门槛。低频试运行降低的是发现成本，不会消除高风险动作本身的责任。

## 企业可以怎样做一次最小验证？

选取一份脱敏样本，把执行频率设为较低水平，使用独立工作目录和测试接收方运行一次。完成后不要只查看最终文件，还要逐项对照输入、过程日志、文件差异和发送记录。若任何一步仍需靠操作者“看情况补一句”，就把该条件补进提示词或任务配置，再重新试运行。

通过标准应是一张可重复使用的检查表，而不是“这次看起来没问题”。当下一位同事在不补充口头背景的情况下也能复现结果，任务才具备扩大调度频率的基础。
