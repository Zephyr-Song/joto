# Dify 企业版私有化交付中，为什么运行手册比部署文档更重要

很多企业推进 Dify 企业版私有化部署时，项目团队最先盯住的往往是安装动作本身：容器是不是起来了，模型接口是不是通了，向量库是不是连上了，知识库能不能导入，Workflow 能不能执行，Agent 能不能跑起来。只要这些功能在验收会上能演示成功，项目似乎就已经“交付完成”。

但站在企业服务商视角，真正影响项目后续口碑和复购的，往往不是部署当天，而是交付之后的三十天、九十天和半年。系统一旦开始接入真实业务，客户团队会持续遇到模型切换、知识库更新、工作流报错、权限变更、接口异常和安全策略调整。如果这些问题只能回头找交付方处理，那这个项目本质上还没有完成接管。

所以，Dify 企业版私有化项目里，部署文档只是起点，运行手册才决定这套系统能不能长期跑在企业内部。

## 部署完成，不等于客户已经具备接管能力

很多项目交付时会提供架构图、服务器清单、端口说明和基础安装步骤，这些内容当然必要，但它们解决的只是“系统怎么搭起来”。企业真正关心的是，系统跑起来之后，谁来管、怎么管、出了问题先看哪里、改动边界在哪里。

比如模型响应变慢，是模型服务本身负载高，还是 Workflow 节点串行太多；知识库回答变差，是新文档没有切片成功，还是旧内容没有失效；某个 Agent 突然无法调用业务系统，是凭证过期、参数变更，还是权限被收回。再比如安全团队提出新增 PII 脱敏要求，运营团队希望调整提示词，业务部门又要求增加一个审批流节点，这些变化都不属于“重新部署”，却每天都在真实环境里发生。

如果没有运行手册，客户只能把所有变化都当成技术故障提交给交付方。久而久之，项目就会从“私有化落地”变成“外包代运维”，系统虽然部署在企业内网，能力却没有真正沉淀到客户团队。

## 一份合格的运行手册，至少要讲清 4 件事

第一，要讲清模型和路由策略。包括当前接了哪些模型，分别服务什么场景，超时和失败如何降级，模型切换会影响哪些应用，哪些参数可以由客户自己调整，哪些改动需要评估。没有这部分，系统出了性能问题，团队只能盲目归因给“大模型不稳定”。

第二，要讲清知识库运营机制。文档从哪里进入，谁负责审核，切片和索引的更新周期是什么，失效资料怎么下线，敏感资料如何隔离，引用来源如何追溯。企业知识库一旦进入生产，就不是一次性导入工程，而是持续治理工程。

第三，要讲清 Workflow 和 Agent 的变更边界。哪些节点是业务同学可以维护的，哪些接口参数必须由技术同学校验，哪些动作需要人工确认，哪些失败场景必须保留审计日志。运行手册如果只讲“流程长什么样”，不讲“谁能改、改完怎么验”，后面就一定会反复踩坑。

第四，要讲清运行时安全与排障路径。输入输出安全规则放在哪里，PII 脱敏在什么环节执行，异常告警打到哪里，日志能追到哪一层，出现误拦截或漏拦截时由谁处理。对企业来说，安全不是部署前做一次评审，而是上线后每天都要持续运转的机制。
